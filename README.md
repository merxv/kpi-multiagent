# 🎯 Многоагентная система формирования KPI на основе стратегии университета

Система принимает документ стратегии (программы развития) университета и строит каскад
**«стратегическая цель → задача → KPI → базовое и целевое значение»**, а затем проверяет каждый KPI
по критериям SMART и возвращает слабые показатели на доработку.

- **6 агентов** с одной ролью у каждого, схема «оркестратор + общее состояние»
- **Локальная модель** `qwen2.5:7b` через [Ollama](https://ollama.com): данные стратегии не покидают компьютер
- **Веб-интерфейс** на Streamlit и **CLI**
- Логирование всех вызовов, лимиты шагов и времени, повторные попытки, контроль нагрузки агентов (≤ 40%)
- **15 тестовых сценариев** с ожидаемым результатом и автопрогоном: пройдено 15 из 15 ([отчёт](reports/scenarios/latest.md))


---

## Почему многоагентная система

Каскадирование стратегии в KPI в вузе выполняют разные специалисты: стратегический офис формулирует цели,
подразделения декомпозируют их, аналитики подбирают показатели и считают значения, служба качества проверяет результат.
Небольшая локальная модель (7B) не справляется со всей цепочкой в одном запросе: контекст ограничен, структура
ответа теряется, а расчёты «в уме» неточны. Поэтому:

| Проблема одного агента | Решение в команде агентов |
|---|---|
| Стратегия, справочник и данные не помещаются в контекст 7B | Каждый агент получает только свой фрагмент |
| Слишком много инструментов у одного агента | У каждого агента ≤ 2 инструментов |
| Модель проверяет сама себя | Отдельный агент-проверяющий с формальными правилами и циклом доработки |
| Ошибки в расчётах | Целевые значения считает код, LLM только обосновывает их |
| Сбой ломает весь результат | Ошибка на одной цели или KPI изолирована |

## Архитектура

| Агент | Роль | Вход → Выход | Инструменты |
|---|---|---|---|
| **Оркестратор** | Планирует и распределяет задачи, управляет доработками. Предметную работу не делает | запрос → план (`horizon_year`, `focus_directions`) | — |
| **Аналитик стратегии** | Выделяет стратегические цели | документ → `[Goal]` | `read_document`, `split_into_chunks` |
| **Декомпозитор целей** | Разбивает цель на измеримые задачи | `Goal` → `[Task]` | — |
| **Конструктор KPI** | Формулирует KPI: название, формула, единица, периодичность, источник | `Task` (+ замечания) → `KPI` | `search_kpi_library` (SQLite), `list_metrics` (CSV) |
| **Агент целевых значений** | Считает базу и цель по тренду, пишет обоснование | `KPI` → `KPI` + значения | `compute_target` (CSV + расчёт) |
| **Проверяющий** | Оценка SMART (1–5), правила в коде, дубли; возврат на доработку | `[KPI]` → статусы, оценки, замечания | `check_kpi_formal`, `find_duplicates` |

Агенты обмениваются типизированными сообщениями `AgentMessage {sender, receiver, type, payload, ts}` (pydantic → JSON).
Все схемы описаны в [kpi_system/schemas.py](kpi_system/schemas.py).

### Как проверяющий принимает решение

KPI отправляется на доработку, если сработало хотя бы одно условие:

1. **Ошибка формальных правил** (`tools/validation.py`):
   - название сформулировано как действие («Повысить…») или дословно повторяет задачу;
   - в формуле нет способа расчёта;
   - не указана единица измерения;
   - цель равна базе или противоречит направлению показателя;
   - процентный показатель больше 100%.
2. **Оценка SMART моделью** (specific, measurable, achievable, relevant, time_bound по шкале 1–5): `relevant` или `measurable` ≤ 2, либо средняя оценка < 3.
3. **Дубль** другого KPI (сходство названий ≥ 0.8).

После `MAX_REVISIONS` кругов доработки KPI получает статус «требует внимания» и передаётся человеку.

## Надёжность

| Механизм | Где | Параметр `.env` |
|---|---|---|
| Лимит шагов (вызовов LLM и инструментов) | `TaskState.tick()` | `MAX_STEPS=150` |
| Лимит времени прогона | `TaskState.tick()` | `MAX_RUNTIME_SEC=1200` |
| Защита от зацикливания доработок | `Orchestrator.run()` | `MAX_REVISIONS=1` |
| Повторы при сбое или невалидном JSON | `OllamaClient`, `BaseAgent.ask_llm()` | `LLM_RETRIES=2` |
| Логирование всех вызовов | `logs/<run_id>.jsonl` | — |
| Явное состояние задачи | `runs/<run_id>.json` | — |
| Не больше 5 инструментов у агента | `BaseAgent` | — |

Ключи и адреса хранятся в `.env` (файл не попадает в git), в коде их нет.

## Быстрый старт

**Требования:** Python 3.11+, установленная [Ollama](https://ollama.com).

```bash
git clone <URL репозитория>
cd multiagent
pip install -r requirements.txt
cp .env.example .env
ollama pull qwen2.5:7b
```

### Веб-интерфейс

```bash
streamlit run app.py
```

Откроется http://localhost:8501. Выберите пример стратегии или загрузите свой файл (TXT, MD, PDF, DOCX),
напишите запрос и нажмите **«Запустить»**. Вкладки интерфейса:
- **KPI**: итоговая таблица и выгрузка в Excel или JSON;
- **Цели и задачи**;
- **Нагрузка агентов**: проверка требования ≤ 40%;
- **Сообщения**: JSON-сообщения между агентами;
- **Лог**: все события прогона.

### Командная строка

```bash
python main.py --doc data/sample_strategy.txt --request "Сформируй KPI до 2030 года, акцент на науке" --max-goals 3
```

### Тесты

Модульные тесты инструментов, правил и лимитов (без LLM, около 1 с):

```bash
pytest -q
```

## Тестовые сценарии

15 сценариев с ожидаемым результатом описаны в [tests/scenarios/scenarios.yaml](tests/scenarios/scenarios.yaml).
Каждый сценарий проверяется автоматически: статус, текст ошибки, число целей и KPI, горизонт, нагрузка агентов, лимиты.

```bash
python run_scenarios.py               # все сценарии, ~10 минут
python run_scenarios.py --only S01,S08
```

Результаты:
- `reports/scenarios/latest.md` — отчёт для сдачи;
- `latest.json` — сырые данные;
- `reports/typical_run/` — лог и состояние типового сценария, подтверждают распределение нагрузки.

Эти же сценарии можно запустить в веб-интерфейсе в разделе **«🧪 Тестовые сценарии»**.

| ID | Сценарий | Что проверяется |
|---|---|---|
| S01 | Типовой: все направления | ≥ 3 целей, ≥ 6 KPI, ≥ 60% принято, покрытие целей, нагрузка ≤ 40% |
| S02 | Фокус на науке | фокус извлечён из запроса, все цели — наука |
| S03 | Горизонт 2028 | год цели у всех KPI = 2028 |

| S07 | Расплывчатая стратегия | нет непредвиденных ошибок, KPI заполнены |
| S08 | Нет стратегических целей | понятное сообщение, 0 KPI |
| S09 | Слишком короткий файл | понятное сообщение |
| S10 | Неподдерживаемый формат | понятное сообщение |
| S11 | Файл не найден | понятное сообщение |
| S12 | Ollama недоступна | «Нет связи с Ollama», без зависания |

Последний прогон (qwen2.5:7b): **15 из 15 пройдено**. На успешных прогонах доля принятых KPI 75–100%,
средняя оценка SMART 3.7–4.2, максимальная доля одного агента 26–34%.

### Метрики качества

После каждого прогона считаются метрики (`kpi_system/quality.py`). Они показываются в интерфейсе и в CLI
и сохраняются в `runs/<run_id>.json`:
- доля принятых KPI;
- доля принятых с первого раза;
- доля KPI с рассчитанной целью;
- покрытие целей;
- средняя оценка SMART;
- максимальная доля одного агента.

```bash
python experiments/single_agent_baseline.py --runs 3   # базовая схема «один агент»

```

| Показатель (S01, S04, S07 × 3 запуска) | Многоагентная | Один агент |
|---|---|---|
| Соблюдён лимит числа KPI | 100% | 67% |
| KPI без ошибок правил SMART | 97% | 77% |
| Цели в пределах ±25% от тренда | 100% | 56% |
| KPI привязаны к данным | 35% | 87% |
| Время прогона | 72 с | 21 с |

Многоагентная система лучше соблюдает ограничения и правила, а её целевые значения рассчитаны по данным.
Один агент работает быстрее и чаще привязывает KPI к метрикам, но в том числе к темам, которых нет в стратегии.

## Ограничения

- Данные вуза в `data/` учебные. Для реальной работы замените `university_metrics.csv` выгрузкой из информационной системы.
- Модель 7B оценивает SMART мягко (обычно 3–5). Поэтому большинство отклонений дают формальные правила в коде и поиск дублей, а не оценка модели.
- Около половины KPI не привязаны к фактическим данным (нет подходящей метрики в CSV): для них целевое значение не рассчитывается, а агент описывает, какие данные собрать.
- Система формирует черновик системы KPI, окончательно утверждает его человек.
